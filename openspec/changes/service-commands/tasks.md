- [x] 5.1 Ship `start`, `stop`, `restart`, `enable` and `disable` workflows with `type = "service"` under `crates/core/tedge_agent/src/resources/`, whose execution step runs `sudo -n tedge service ${.topic.operation} ${.payload.serviceName} --service-type ${.payload.serviceType}`. A template is created when missing and never overwritten once it differs from the shipped copy, so an administrator can adapt a workflow or drop it altogether
- [x] 5.2 Give each workflow a timeout so a backend that never returns ends as `failed`. A script step ignores `on_timeout`: a step that times out is killed, so the reason is declared with `on_kill`. The timeout is 180 seconds, twice what systemd itself waits to stop and to start a unit; `enable` and `disable` take 60, nothing waiting for the service to change state
- [x] 5.3 Implement the agent self-restart case with the existing pattern — `action = "restart-agent"` then `await-agent-restart` (`crates/extensions/tedge_config_manager/src/resources/config_update.toml:26-39`) — so the step is not re-executed on resume. The agent asks its runtime to stop rather than asking a backend to restart it, which also covers `tedge run all`, where the agent is co-hosted with the mappers and no `tedge-agent` unit exists for a backend to act on
- [x] 5.4 Reject `stop` addressed to tedge-agent or to a cloud mapper with a reason naming why. Four guard steps do it argv-only, with no shell: `test <name> = tedge-agent`, then `test <name> = tedge-mapper-collectd` and `test <name> = tedge-mapper-local` to let those two through, then `expr <name> : tedge-mapper-`, each `test` accepting the `.service` spelling of the name as well, since an init system knows the same service under both. ## 13. Decisions to revisit

Open questions raised while reviewing group 11.

- [x] 13.1 **Decided.** The mapper publishes no fallback name, and it does validate the name it is given. A `c8y_ServiceCommand` carrying no `serviceName`, or one that breaks the service name rule of `tedge service`, fails the cloud operation with that as its reason. Cumulocity's own contract always sends the field, so a missing name is treated as an invalid one rather than as a case to recover from. Deriving the name from the entity instead was considered at length and dropped: Cumulocity holds a single `name` per service, which is the value thin-edge itself published in the `102` message, so the cloud carries thin-edge's own registration data back and can hold nothing the mapper does not already have. Nothing in the registration data means "the name the backend knows" — neither the `name` nor the service segment of the topic identifier is guaranteed to be it — so choosing one of them over the cloud value would be a silent guess, and it would drop the value the operator reads on the operation. Which name a service is reachable by is a contract on whoever registers it, now stated in the user guide. The `nodered` / `Node-RED` case that raised the question is answered by the rule, not by the mapper: such a service is registered with a `name` its backend does not know, and the backend says so
- [x] 13.2 **Decided.** The rule is now `[a-z][a-z0-9_-]*`, and it is derived rather than chosen: it is the largest set of characters left once every step a name takes has had its say. Lowercasing by the c8y mapper rules out uppercase; the `cmd/<action>` topic segment rules out `/`, `+`, `#` and spaces; being one argument of an init tool or of a plugin rules out a leading `-` and shell metacharacters; being a key of `[init]` in `system.toml` requires a TOML bare key, which is what rules out `.` and `@` even though a service name accepts both. So the action rule and the service type rule end up identical — both name something thin-edge chooses — while the service name rule stays wider, since a unit or container name is not thin-edge's to choose. Widening one character at a time as a case appears was the thing to avoid, and this rule answers the next character too. `-` also gives a way around the reserved `[init]` keys: an "is active" action can be named `is-active`. The 2-character minimum was dropped in the same move; nothing in the list above rejects a one-letter name, so there was no reason behind it. Not done: a note recommending `_` over `-`. A custom action name is the user's to pick; the `_` convention binds only the names thin-edge ships. The reasoning is recorded in `design.md` and in 0011, and the spec files and the three `docs/src/` pages state the rule only. Deriving this rule showed that the other two are not derived, which `design.md` now says as well. The service name rule is a whitelist: only its leading `-` comes from a step the name takes, and the rest is there because the name comes from the cloud and then reaches code thin-edge does not own — an `[init]` template is an argv list the user writes, so it can be `["/bin/sh", "-c", "systemctl restart {}"]`, and a plugin may be a shell script using its arguments unquoted. The doc comment of `validate_service_name` claimed the opposite, "even though nothing runs it through a shell", and was rewritten. The service type rule keeps its traversal guard as its own constraint and follows the action name's rule for the rest; its lowercase restriction is a chosen canonical spelling, not a derived one — raised and left as is

## 15. To consider later

Nothing here needs to change now.

- [ ] 15.1 Whether `disable` refuses the services `stop` refuses. `stop` refuses `tedge-agent` and any cloud mapper because the outcome of the command asking for it could not be reported. That reason does not hold for `disable`: a disabled service keeps running, so the outcome is reported. The risk is a different one — disabling `tedge-agent` leaves the device unmanaged after the next reboot, and nothing fails at the time of the command, so the operator learns of it only when the device stops reporting. Decide whether that deserves the same refusal, for that different reason

- [ ] 15.2 Whether a service maps every `cmd/<action>` to `c8y_SupportedServiceCommands`, or only some of them.
  The mapper takes every command capability of a service as an action of that service (`crates/extensions/c8y_mapper_ext/src/converter.rs:1144`),
  so no device operation is ever declared on a service,
  and it reports the outcome of every command of a service as `c8y_ServiceCommand`, deciding that from the entity type alone (`crates/extensions/c8y_mapper_ext/src/operations/handlers/mod.rs:95`).
  That convention is what dropped `service-supported-ops.robot`, whose tests covered a service's `cmd/<action>` becoming an operation of its own.
  It may be wider than it has to be: a `c8y_LogfileRequest` on a service is a reasonable thing to ask for, and the discussion which settled the convention did not cover it.
  What the convention costs today is small.
  No component declares a device operation on a service, so such an operation reaches one only when it is created on that service's managed object through the REST API,
  none of the inbound converters checking the type of the target they resolve.
  It is then carried out only if a workflow is registered for it under `type = "service"`,
  which for the shipped set means `restart` alone, `service_restart.toml` being the one whose name is also a device operation.
  The outcome is reported as `c8y_ServiceCommand`: with `smart_rest_use_operation_id` the status is set by operation id, so the operation still closes,
  and what is lost is the work the mapper does for that operation in particular — uploading the log file or the configuration file it was asked for.
  Decide the declaration side first, the reporting side following from it.
  Making the reporting exact now — by refusing a device operation addressed to a service where the target is resolved (`process_json_over_mqtt`, `converter.rs:515`),
  or by reading the declared set instead of the entity type — would fix the current convention in place, which is the opposite of leaving the question open
